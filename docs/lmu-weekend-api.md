# Local LMU weekend integration

## Explicit API consent

`detectOwnedContent`, `previewLmuWeekend`, `applyLmuWeekend` and `startLmuWeekend` share a memory-only consent gate. The modal starts unchecked and requires both the checkbox and a separate acceptance click. Cancel, Escape, backdrop dismissal or replacement grants nothing. Concurrent requests share one prompt. Revocation invalidates pending acceptance; Settings can revoke an accepted session, and reload/close clears it. Manual configuration/start and all XML processing bypass this gate.

The notice and related actions/errors are translated into all seven languages on this branch (English source plus Italian, German, French, Spanish, Brazilian Portuguese and Korean). It describes undocumented-API risks and separates responsibility for this fork's integration from the original author's development, maintenance and support. It does not claim an absolute legal waiver. The bridge attaches `apiConsent: true` and `apiConsentVersion: "lmu-api-v1"` to each API request; the backend checks both before dispatch. These flags enforce the normal application flow, not authentication against a modified client. Revocation does not undo previously sent/in-flight commands.

Validation: 39 JavaScript tests and 267 Core tests pass; the Windows solution and desktop consent tests cross-compile. A browser check exercises the real modal lifecycle and bridge with startup routing suppressed and simulated backend replies: every language renders, checkbox alone sends nothing, cancel/Escape/backdrop deny access, session reuse works, revocation re-prompts, and manual calls remain independent. The inline replacement check also covers cancellation, mode changes and duplicate acceptance clicks. Desktop test execution still requires Windows. The earlier dual-mode ZIP does not contain this later consent change.

Protocol checked against the running LMU build 14200 on 2026-10-26, Swagger and the game's own `/start/assets/app-g29PuqnE.js`. These internal endpoints may change between game versions. Mocked tests validate the implementation. On 2026-10-27 the user confirmed that all configured settings were received in a Windows test. Their screenshot shows LMU v1.4200 loaded at Lusail, with open practice (60 minutes, 13:00) and private qualifying (10 minutes, 14:00) selected in Factory Seat. This confirms the reported configuration, not exhaustive coverage of all modes or completed XML result import. Skipping and other P/Q combinations still require live verification.

- Normal menu launch accepts `/navigation/state` with `NAV_MAIN_MENU`, `SETTING_GRANDPRIX`, `GSTATE_SETUP`, and an explicitly false loading flag. Captures from the user show LMU can retain `NAV_EVENT` / `GSTATE_DYN` even while its home/configuration UI is visible; those values alone do not prove the player is driving. For that exact offline/non-loading state, additionally read `/rest/sessions/GetGameState`. Only explicit `inMonitor: true`, `isReplayActive: false` and `playerVehicleLoaded: true` permit offering a separate replacement confirmation. Before confirmation the preview fails with `lmu-offline-session-confirmation-required` and writes nothing. An inline warning in the weekend form explains that any loaded offline session will be replaced and unsaved progress may be lost. A fresh unchecked checkbox and explicit **Replace session and launch** click are required. Cancel or switching modes discards permission; checking the box alone sends nothing. Permission is passed only for that new launch attempt and bound to its expiring preview plan/token; apply and every verification recheck the simulation. Driving outside the monitor, replay, multiplayer, loading and unknown states remain blocked. No automatic exit-session command is sent.
- GET `/rest/sessions/getTracksAll`: exact `cmpName` + mapped `sceneDesc`, with `isOwned: true`. Layout mappings are explicit in `LmuTrackLayouts`, not inferred from translated display names.
- GET `/rest/sessions/getAllVehicles`: owned car matching the catalog folder in `vehFile`, and the briefing's number/team numbers when specified. An arbitrary accessible livery is only chosen when the briefing allows any livery. Custom Race Control teams are not automated yet.
- GET `/rest/garage/UIScreen/SessionSetup`: read back `trackInfo` and `selectedCar`.
- POST `/rest/sessions/SessionPresets/requestPreset` with JSON `null` reads the current preset; despite its HTTP verb, it does not apply settings or start the game.
- POST `/rest/race/track`: plain-text track ID. POST `/rest/garage/SetCurrentVehicle`: text body containing JSON `{ "id": "vehicle-id" }`, matching LMU's frontend.
- Re-read the preset after selections, modify only briefing-owned fields, then POST `/rest/sessions/SessionPresets/applyPreset`: `Player["Game Options"]` fields `Race Time` (minutes), `Race Finish Criteria` = 2 (time rather than percentage), `Fuel Consumption Multiplier`, `Tire Wear Multiplier`; `Player["Race Conditions"]` fields `RaceStartingTime` (minutes from midnight, -1 for default), `RaceTimeScale`, `Num Race Sessions` = 1.
- Optional practice/qualifying choices use `Player["Game Options"]` fields `practice length` and `qualifying length` (minutes); `Player["Race Conditions"]` fields `Run Practice1` through `Run Practice4`, `PrivatePractice` (boolean), `Practice1StartingTime`, `Num Qual Sessions`, `PrivateQualifying` (0=open, 1=private), and `QualifyingStartingTime`. Skip disables all practice slots or sets the qualifying count to zero, preserving hidden duration/privacy/time values. Open/private enables exactly one respective session. Keep changes nothing. Start times are minutes from midnight or -1 for the circuit default. Only the previously observed fields/modes are exposed; additional qualifying enum values are not guessed. Simulated responses cover all exposed choices; the Windows confirmation above covers open practice and private qualifying.
- Do not use `/rest/sessions/settings` for absolute values: its `value` is a relative step. In particular `SESSSET_race_time` is not race minutes.
- Read every briefing field and explicit P/Q choice back before enabling launch. Weather, grip, warmup, difficulty and the AI grid are not chosen by Factory Seat; LMU can adjust defaults during selections. Review them in the game.
- A separate confirmed launch revalidates settings, POSTs the current preset to `/rest/sessions/SaveLoad/generateSaveFileFromSessionPreset`, validates the returned `SessionPreset`, arms and saves career result tracking, then POSTs `{ "save": generatedSave }` to `/rest/sessions/SaveLoad/loadGame`. This follows the modern game UI, rather than assuming the old `startRace` endpoint launches an offline weekend.
- `/rest/race/getAllowedToStartRacing` is used by the in-session drive/continue UI, not as the main-menu weekend launch gate.

Previews expire after five minutes and are bound to the career/briefing. Configuration changes since preview invalidate it. Applying never launches. Partial failures do not roll back unrelated game changes or claim success. Start tokens are consumed before launch; a timeout must not cause an automatic retry because the game may already have received the command. XML remains the only results source.

## Unified per-race configuration (UI R3)

The next-race screen now presents inherited track/layout/car information and one event-settings form, not manual checkboxes. `saveWeekendConfiguration` validates and persists race length, fuel, tyres, time scale, start time and P/Q choices on the upcoming round. Global P/Q settings are defaults only for rounds without saved choices. Active/completed/skipped rounds and stale round numbers cannot be edited. Race settings update the same round fields used by XML matching, and the pit-plan stint count is recalculated from the saved length and fuel consumption. Track, car and points weight are not editable here.

Manual and assisted starts are first-class options in the same form. **Manual** is selected by default. **Start manual weekend** calls only `startManualWeekend`: it validates/saves the configuration and arms the local round, without constructing an LMU client, checking game availability or sending any game API request. Existing `ResultsWatcher`, XML parsing and matching behavior are unchanged. The same expected-round guard used for configuration prevents a stale manual action from starting a different round.

Selecting **Assisted (LMU API)** and clicking **Launch weekend in LMU** explicitly authorizes saving that configuration, preparing a preview, applying, reading back, and finally calling the separately guarded start endpoint. No game API probe runs just because the page opens or the mode changes. LMU must already be running at the offline menu; this flow does not start the game executable from a closed state. The internal API is not guaranteed stable across patches: live schema/selection checks and readback happen for each attempt, rather than relying on a startup check or claiming version compatibility.

An unavailable preview keeps Assisted selected and shows the error; manual remains an explicit alternative. A rejected menu check includes only the observed navigation state, setting mode, game state and loading flag, not user or car/track payloads. Apply errors or failed verification may have changed settings but never send a load command; the UI disables further assisted attempts until reopened, while manual start remains available. An uncertain load also returns to manual mode, locks configuration editing and offers **Continue manually** with an instruction to check LMU first. `startManualWeekend` is idempotent for an already armed round: it preserves `ArmedAt`, saved settings and earlier XML eligibility rather than resetting them, and it never sends a load command. If the assisted path failed before arming, the manual endpoint saves and arms normally. No configuration/launch error automatically resets, skips or ends a career round.

Launch diagnostic build: 36 JavaScript and 260 Core tests pass, including the captured `NAV_EVENT` / `GSTATE_DYN` rejection with no game writes. This improves feedback and prevents implicit mode switching after a preview failure; it does not establish that the live Windows launch issue is resolved. The menu allowlist has not been relaxed without evidence of a safe additional state.

Subsequent retained-session fix: a user capture from the home UI reports `NAV_EVENT`, `SETTING_GRANDPRIX`, `GSTATE_DYN`, `loading: false`; `GetGameState` reports `MONITOR_MENU`, `inMonitor: true`, `isReplayActive: false`, `playerVehicleLoaded: true`, `GPHASE_CHECKERED` and `inControlOfVehicle: true`. Treat the API as reporting a retained or loaded session, not as reliable evidence of the current visible screen. The confirmed replacement path described above reproduces these relevant fields in tests and verifies one load after arming, denial without confirmation, and blocking if the player leaves the monitor before apply/start.

The first replacement-modal build was reported to cancel even after acceptance on Windows. Its packaged source and browser modal checks returned acceptance correctly; that platform-specific failure has not been reproduced. Replacement authorization now lives directly in the weekend form rather than relying on the modal result. JS tests cover unchecked defaults, no request on checking/cancelling, permission passed only on explicit acceptance and a fresh unchecked prompt on a later attempt. This is a workaround for the reported cancellation path, not a claim that its root cause has been identified. API consent remains in its independent checkbox modal.

On 2026-10-27 the user confirmed that the inline-confirmation Windows build successfully initiated the assisted launch; their screenshot shows LMU v1.4200 loading Imola at 74%. This confirms a real game-loading request after the fix, not completion of the load, verification of every in-game setting, or a completed-race XML import. Those checks and desktop test execution remain outstanding.

The career currently stores the player's car class, not a separate selected opponent-class composition. The AI grid/opponent classes are still LMU-controlled; no class selection is inferred from an event name or silently sent to the API. Supporting inherited opponent-class selections requires modeling them in the preceding phase and verifying LMU's grid protocol.
